# たまごの孵化ペースと見た目の段階 — 再設計の前提（2026-10-21）

> **このファイルの役割**: 再設計（要件定義・経済設計）を始める新しいセッションへの引き継ぎ。
> 現状の数字はすべてコードから確認済み（推測ではない）。**決めるのはここから**。
> 推奨設定: **Fable 5.1 / 最大**（複数案を比べるなら Ultracode）— 経済設計は一度間違えると全ユーザーの体験に響くため。

## 1. オーナーの要望（原文の要旨）

1. 今だと**全然孵らない**と感じる。「SNSを全くやらない人で**1週間に1個**」は早すぎるか？
2. 今の見た目は「たまご／ヒビ1／ヒビ2／孵化」で、**ほとんど変わらないので飽きる**。
   **1日1回開くとして7つの大きな変化**があるとよいのでは？
3. **続けた時間よりも、SNSをやめた時間を考慮したい**。

## 2. 現在の仕組み（コードで確認済み）

### ポイント計算（サーバー `fn_finalize_day` が正。最新定義は `supabase/migrations/0016_ledger_source_key.sql`）

```
基準分   = max(直近7日の確定済み利用の平均, 30分)      ← 30分は下限（baseline_floor_min）
削減pt   = max(基準分 − 今日の利用分, 0) × 1pt/分
最終pt   = min(floor(削減pt × 連続倍率), 480)          ← 480は1日上限（daily_point_cap）
連続倍率 = 1日目×1.0 / 3日目×1.2 / 7日目×1.5 / 30日目×2.0（streak_multipliers）
連続は「その日の削減が0」でリセット（開かなかった日ではリセットされない）
```

- 孵化しきい値: **500pt**（`egg_thresholds.hatch`）。ヒビ1=100 / ヒビ2=250 は値だけ存在。
- 初回ボーナス: 1日目200pt＋2日目300pt＝ちょうど500＝**2日続けて開けば最初の1個は必ず孵る**。
- クライアントの `lib/core/usage/point_calculator.dart` は同じ式の暫定版（確定はサーバー）。

### 計測の制約

- **iOS は分単位の利用時間を取れない**。DeviceActivity のしきい値通過だけが分かる。
  しきい値は `ios/Runner/ScreenTimeShared.swift` の `[15, 30, 45, 60, 90, 120, 150, 180, 240, 300]` 分。
  → 1時間までは15分刻み、3時間までは30分刻み、5時間超は「5時間超」としか分からない。
- **iOS はアプリを入れる前の利用時間を読めない**（監視は開始時点から）。
  したがって基準分は「入れたあと＝すでに減らそうとしている時期」の時間から作られる。
- iOS は**対象アプリを選ばないと永久に0分**（2026-10-05 に判明・PR #106 で案内を追加済み）。

### たまごの見た目（`lib/core/widgets/egg_art.dart`）

- 進捗 0〜20%: ヒビなし（ゆっくり呼吸する動き）
- 進捗 20%〜: **1本のヒビの線が少しずつ伸びる**＋揺れる動き
- **「ヒビ2」に当たる絵は存在しない**。実質「ヒビなし → 1本のヒビが伸びる」の2段階で、
  しかも連続的に伸びるので**日ごとの差がほぼ見えない**（オーナーの指摘どおり）。

## 3. 現在の式で計算した孵化ペース（シナリオ試算）

### A. SNSを全くやらない人（毎日開く）

基準分は下限の30分に張り付く → 毎日 30pt × 連続倍率。

| | 1日のpt | 孵化まで |
|---|---|---|
| 1個目 | 初回ボーナス | **2日目**（2日続けて開いた場合） |
| 2個目 | 30→36→45 | **13日目** |
| 3個目以降（連続7〜29日） | 45 | 約**11〜12日**に1個 |
| 連続30日以降 | 60 | 約**9日**に1個 |

→ オーナーの「全くやらない人で1週間」に対し、**現状は約1.5〜2倍遅い**。

### B. 1日2時間 → 30分に減らした人（減らす前の7日分の記録がある場合）

基準分が自分の新しい（少ない）利用時間に引きずられて毎日下がる。

| 減らして何日目 | 基準分 | 削減pt | 連続倍率込み |
|---|---|---|---|
| 1 | 120 | 90 | 90 |
| 2 | 107 | 77 | 77 |
| 3 | 94 | 64 | 76 |
| 4 | 81 | 51 | 61 |
| 5 | 69 | 39 | 46 |
| 6 | 56 | 26 | 31 |
| 7 | 43 | 13 | 19 |
| **8日目以降** | **30** | **0** | **0（連続もリセット）** |

→ 1日90分もSNSを減らすという大きな成功をしても、**最初の1週間で約400pt（1個に届かない）**、
**8日目以降は毎日0pt**。減った状態を続けるほど報われなくなる。

**これがオーナーの言う「続けた時間よりやめた時間を考慮したい」の核心**:
今の式は「前の週よりどれだけ減らしたか（＝変化）」を数えており、
「SNSから離れていた時間（＝状態）」は、1週間で数えられなくなる。

### 補足: 実データ（2026-10-05 / ORG_STATE）

- 削減ptを得たのは全期間で**6人**。育成中の卵91個のうち83個が初回ボーナスの200ptで停止。
- オーナー自身の iOS アカウントは3か月で186pt（対象アプリ未選択で0分 → 下限30ptが開いた日だけ入っていた）。

## 4. 中身の量（ペースを上げても枯れないか）

- 図鑑は20種×2色＝40エントリ（`dex_total_entries`）。進化は同種3体で成体（`mofi_evolve_stage2_count`）。
- 通常のたまごのSSR率は**0.3%**（`drop_tables` normal: common 80% / rare 17% / sr 2.7% / ssr 0.3%）
  → SSRを1体出すだけで通常のたまご平均**約330個**。
- → **1週間に1個でも中身が枯れる心配はない**。ペースは「飽き」と「達成感」だけで決めてよい。

## 5. 決めること（再設計セッションの議題）

1. **基準をどこに置くか**（オーナーの要望3）
   - 案A: 基準を「最初の計測週」に固定し、下がり続けないようにする（ずるの対策が要る）
   - 案B: 絶対的な目標（例: 1日◯分以内）に対して、どれだけ離れていたかで数える
   - 案C: 1日の結果を「◎／○／△」の評価にし、評価ごとに**段階を何段進めるか**を決める
     （分単位を直接ポイントにしない。iOS の粗い計測とも相性が良い）
2. **「1週間で1個」を誰の基準にするか**: 「SNSゼロの人が1週間」か「しっかり減らした人が1週間」か。
   前者なら普通に減らした人は10日前後、後者ならゼロの人はもっと速い。
3. **7段階の中身**（オーナーの要望2）。毎回「違う種類の変化」にすると見分けがつく。
   たたき台: ①新しいたまご ②ぬくもり（レア度の色がにじむ）③鼓動（ときどき揺れる）
   ④最初のヒビ ⑤中が透ける（中の子の色や模様がうっすら見える）⑥光が漏れる ⑦孵化
4. **段階が進んだ瞬間の演出**。連続的に少しずつ変わるのではなく、開いたときに
   「変わった！」と分かる見せ方（段階ジャンプ＋短い演出）にしないと、7段階にしても気づかれない。
5. **悪い日をどう扱うか**。0ptの日が続くと離脱する（実データで2日目離脱が最大の穴）。
   悪い日でも「少しだけ進む」にするか。
6. **移行**: 既存の卵（200ptで止まっている83個など）を新しい段階にどう対応させるか。
7. **変更範囲**: サーバー（`app_config` の値・`fn_finalize_day`・段階の定義）＋クライアント（絵・演出）
   ＝**両ストアのアップデートが必要**。値だけで済む部分（しきい値・倍率）はアプリ更新なしで変えられる。
